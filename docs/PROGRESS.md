### Consolidated schema script (2026-08-21)

The live project was re-probed and **phases 2, 3 and 4 are now applied** — `work_logs`, `tasks`, `observations`, `sessions` and `session_corrections` all exist, and each returns `42501` for the anon key, which is the grant/RLS block those migrations create (`revoke all from anon, authenticated` then `grant select … to authenticated`). Phases 5 and 6 are still missing: `integrations`, `integration_sync_runs`, `workflows`, `workflow_runs`, `notifications`, `notification_preferences` and `approvals` all return `PGRST205`, which is why the workflows screen reports *"Could not find the table 'public.workflows' in the schema cache"*.

Because the schema is split across five versioned migrations, applying it by hand meant pasting five files into the SQL Editor, in order, one at a time — and each missing table surfaced as its own error. To remove that friction:

- **`supabase/apply-all.sql` was added** — the same statements as the five migrations, concatenated in the same dependency order, plus a final `notify pgrst, 'reload schema';`. It is a *derived* artefact: `supabase/migrations/*.sql` remains the source of truth, and the header says so. It sits in `supabase/`, not `supabase/migrations/`, so `supabase db push` still sees only the five versioned files.
- **Validated against PostgreSQL 18** with the Supabase roles emulated, in four cases:
  - **Empty database** → exit 0; all 12 tables created; RLS enabled on 12 of 12; the `supabase_realtime` publication ends up holding all 12 tables.
  - **Phases 2, 3 and 4 already applied** (the live project's state) → exit 0; the earlier phases re-apply as `NOTICE … already exists, skipping` with no error and no schema drift, then phases 5 and 6 are added; all 12 tables present, RLS 12 of 12.
  - **Applied twice more on top** → exit 0 both times, identical table set and publication — idempotent.
  - **Write path and RLS on the final schema** → `work_logs.id` default is `gen_random_uuid()`; an insert that omits `id` (as the client does) succeeds; `user_id` is auto-stamped from `auth.uid()`; `anon` is refused on both `work_logs` and `workflows` with `permission denied`.
- The trailing `notify pgrst, 'reload schema';` matters: PostgREST validates table and column names against an in-memory snapshot, so a freshly migrated table keeps returning `PGRST205`/`PGRST204` until the cache is reloaded.

**NOT verified:** the script was not run against the live project — there is no `service_role` key, database password or management token in this environment, so it still has to be applied from the Supabase SQL Editor.
